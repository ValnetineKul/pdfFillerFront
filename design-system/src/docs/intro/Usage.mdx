# Применение компонентов из дизайна системы

## Введение

Когда речь идет о **DS** с точки зрения разработки,
важно, чтобы разработчики следовали установленным правилам и учитывали ограничения,
предусмотренные **DS**.
Это необходимо для поддержания целостности интерфейса и согласованности компонентов.
Ниже приведены основные принципы:

## Как использовать ?

Чтобы начать, необходимо установить пакет.
Если у вас уже установлен пакет **DS**, убедитесь,
что у вас установлена актуальная версия.

```bash
pnpm add @front/design-system
```

Все компоненты доступны в одном пакете для упрощения управления зависимостями.

```code
import { TextField } front ‘@front/design-system’;
```

Для использования не стилизованных компонентов прямо из библиотеки **RAC** мы также обращаемся к вложенному директории /base
Компоненты именуются с приставкой Aria

```code
import { AriaTag } front ‘@front/design@styled-system/base’;
```

> Если компонент недоступен для импорта, проверьте, что он существует в StoryBook, его название совпадает с используемым при импорте, и в описании есть пример правильного импорта.

**После установки пакетов необходимо сгенерировать стили Panda**

```bash
pnpm panda codegen --clean
```

### Иконки

Иконки импортируются по примеру остальных компонентов.
Если вам необходимо найти определенную иконку вы можете найти иконки в StoryBook в разделе `System/Icons`.

```
import { DotIcon } front ‘@front/design-system’;
```

### Компоненты

- Настройка компонентов: компоненты должны настраиваться через предоставленные API. Они заранее оснащены всеми необходимыми пропсами,
  обеспечивающими максимальную гибкость для применения и решения бизнес-задач.

---

### Специфичные компоненты

В случае если базовые компоненты **DS** не отвечают бизнес требованиям и
вам необходимо доработать его в рамках бизнес логики которая относится только к определенному проекту.
Тогда есть разные сценария:

- Вы можете использовать компоненты из **DS** как основу для решения.
  Например, создавая `PhoneInput`, возьмите `TextField`, добавьте Select через `contentStart`, и получите `PhoneField` с выпадающим списком для кодов страны.
  Этот компонент можно переиспользовать в любой форме.
  Чтобы избежать дублирования, мы добавляем Stories на уровне проекта.
  Это позволяет другим разработчикам убедиться, что нужный компонент уже существует,
  прежде чем создавать новый.
  Это также упрощает разработку, создавая среду для работы с компонентом без необходимости загружать весь проект.

- Что если ни один компонент не подходит визуально, но логика поведения компонента подходит?
  В таком случае мы можем импортировать не стилизованных компонентов из вложенности `/base`. Также создать отдельный компонент с добавлением специфичных стилей.
  В таком случае мы используем атомарные рецепты такие как [cva](https://panda-css.com/docs/concepts/recipes#defining-the-recipe) или [sva](https://panda-css.com/docs/concepts/slot-recipes#defining-the-recipe) в зависимости от сложности компонента.
  Чтобы избежать дублирования, мы добавляем `Stories` на уровне проекта.

  > Важно понимать, что этот подход применяется редко и только при острой необходимости.
  > Обычно компоненты из **DS** способны решить бизнес-задачи и соответствуют визуальным требованиям.
  > Обязательно проконсультируйтесь с дизайнером о необходимости внедрения данного компонента.

  > Совет: Если подходящий компонент уже существует, но он применяется иначе или решает немного другие задачи. Убедитесь что он наверняка вам подходит. Так как добавление логики в компонент приведет к трудностям поддержке и может затронуть логику работы в других местах применений.
  > В таком случае лучше создать отдельный компонент который будет решать именно ваш сценарий.

### Замена старых компонентов на новые.

При замене старых компонентов на новые убедитесь что новый компонент полностью выполняет требования бизнес логики.
Также убедитесь, что соседнии компоненты, обертки и композиция в целом отображается и ведут себя корректно.

---

### Использование токенов

При использовании **PandaCSS** у нас также есть доступ до токенов из **DS**. Все токены именуются в соответствии с **DS** в Figma.

- **Консистентность:** Используйте дизайн-токены для всех ключевых стилей,
  таких как цвета, отступы, размеры шрифтов, тени, радиусы границ и т.д.
  Это гарантирует, что **DS** остается унифицированной и легко масштабируется.

- **Избегайте "жестких" значений:** Никогда не указывайте значения напрямую (например, цвета или размеры).
  Всегда используйте токены, чтобы сохранить гибкость системы для будущих изменений.
  Иначе, цвета в другой теме не будут перекрашены, и размеры не будут преобразованные если мы будим использовать другие единицы измерения например Rem.

- **Докладывайте о недостающих токенах:** Если токен для необходимого вам свойства отсутствует,
  обратитесь к команде дизайнеров для обсуждения и возможного добавления новых токенов.

### Темы и перекраска компонентов

В случае когда мы используем готовый компонент и выявили что компонент не соответствует дизайну из другой темы.

- Первым делом мы можем протестировать изображение компонента при переключении тем в Storybook **DS**.
  Если перекраска компонента работает корректно в Storybook.
  Тогда следующим шагом надо найти токены в файлах **DS** которые он применяет для другой темы
  `/src/theme/[theme name]/semantic/color/[search for name of component]`,
  и продублировать их в точно такой же папке на проекте по месту применения.
  На примере `public-client` папка находится `src/theme/preset/`.

[Узнайте больше о работе с темами](/docs/intro-theme--docs)

### Доступность

Все компоненты **RAC** используют спецификации WAI-ARIA,
что обеспечивает высокую доступность.
Разработчики должны внимательно следовать этим стандартам при создании пользовательских интерфейсов.
Следуя документации **RAC** можно легко обеспечить доступность добавляя `aria-label`,`aria-labelledby`, `textValue`
где это необходимо. **RAC** предупредит в консоли, если метка отсутствует.
