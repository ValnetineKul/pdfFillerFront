# Разработка в дизайн системе.

## Введение

Когда речь идет о **DS** с точки зрения разработки,
важно, чтобы разработчики следовали установленным правилам и учитывали ограничения,
предусмотренные **DS**.
Это необходимо для поддержания целостности интерфейса и согласованности компонентов.
Также все существующие компоненты должны отвечать регламентам общепринятых практик [(W3C)](https://www.w3.org/) по разработке веб компонентов.
Ниже приведены основные принципы:

### Использование токенов

- **Консистентность:** Используйте дизайн-токены для всех ключевых стилей,
  таких как цвета, отступы, размеры шрифтов, тени, радиусы границ и т.д.
  Это гарантирует, что **DS** остается унифицированной и легко масштабируется.

- **Избегайте "жестких" значений:** Никогда не указывайте значения напрямую (например, цвета или размеры).
  Всегда используйте токены, чтобы сохранить гибкость системы для будущих изменений.
  Иначе, цвета в другой теме не будут перекрашены, и размеры не будут преобразованные если мы будем использовать другие единицы измерения например Rem.

- **Докладывайте о недостающих токенах:** Если токен для необходимого вам свойства отсутствует,
  обратитесь к команде дизайнеров для обсуждения и возможного добавления новых токенов.

### Компоненты

- **Выбор компонентов:** Когда есть необходимость создать новый компонент которого ещё нет в **DS**.
  Важно провести исследование библиотеки **RAC**, на наличие компонента который сможет покрыть необходимые потребности.

- **События:** Компоненты **RAC** предоставляют полный набор событий и состояний,
  таких как `onPress`, `onFocus`, `onBlur`, `isSelected`, `isPending`, `isPressed` а также работу с состояниями фокуса и активности элемента.
  Вы должны управлять этими состояниями через предоставленные `API`, чтобы оставаться в рамках стандарта доступности.

- **Доступность:** Все компоненты **RAC** используют спецификации `WAI-ARIA`,
  что обеспечивает высокую доступность.
  Разработчики должны внимательно следовать этим стандартам при создании пользовательских интерфейсов.
  Следуя документации **RAC** можно легко обеспечить доступность добавляя `aria-label`, `textValue` где это необходимо.

  > Дополнительно в `Storybook` установлен дополнительный пакет тестирования доступности.
  > [Ознакомиться с тестированием](/docs/intro-testing--docs)

- **Семантика:** Компоненты работают с правильной семантикой `HTML` (кнопки, ссылки, формы),
  что улучшает взаимодействие для пользователей с технологиями доступности. Важно изучить анатомию реализуемых компонентов,
  чтобы в полной мере обеспечить правильную основу для среды доступности.

### Стилизация

- **Рецепты:**
  > "Recipes — это конфигурации для стилизации компонентов. Это наборы правил, которые использует PandaCSS для генерации итогового CSS."

Когда мы разрабатываем компоненты, важно определить структуру компонента.
Если структура компонента простая например как кнопка в которой только один тэг `<button>`,
то мы используем конструкцию [defineRecipe](https://panda-css.com/docs/customization/config-functions#definerecipe), если структура сложная и у компонента
есть множество дополнительных взаимосвязанных элементов, то применяем [defineSlotRecipe](https://panda-css.com/docs/customization/config-functions#defineSlotRecipe).

> Обратите внимание на то, что внутри рецепта каждого из ранее написанных рецептов мы добавляем `staticCss: ['*']`, это используется для генерации классов CSS для проекта.
> Без этого стили не соберутся в полной мере, в итоге будут визуальные баги.

- **Условия:** При написании стилей вам может потребоваться применять конкретные изменения в зависимости от определенных условий,
  будь то брейкпоинт, псевдосостояние `CSS`, медиа-запрос или пользовательские `data-атрибуты`.
  Panda позволяет вам писать условные стили и предоставляет удобные сокращения для часто используемых
  условий, чтобы упростить процесс. Допустим, вы хотите изменить цвет фона кнопки при наведении на неё курсора.
  Вы можете сделать это следующим образом:

```
<button
  className={css({
    bg: 'red.500',
    _hover: { bg: 'red.700' }
  })}
>
  Hover me
</button>
```

Узнайте больше о возможностях [условий в стилях](https://panda-css.com/docs/concepts/conditional-styles)
[список встроенных условий](https://panda-css.com/docs/concepts/conditional-styles#reference)

> Также список можно дополнять своими условиями в файле. (design@styled-system/src/preset/conditions/index.ts)

- **Состояния:** - компоненты библиотеки **RAC** уже имеют встроенные состояния которые мы получаем в виде аттрибутов на
  отдельных элементах `HTML` или через пропсы. Наша задача заключается в том, чтобы дописать стили в соответствии с этими состояниями в рецепте.

#### **Пример с аттрибутом**.

Допустим у кнопки в момент клика добавляется аттрибут `data-pressed`. В таком случае мы можем описать данный аттрибут в списке **условий** о котором мы говорили ранее.

> Надо убедиться, что у нас есть необходимый параметр в списке допустимых условий.

```
export const conditions = {
  extend: {
    hovered: '&[data-hovered="true"]',
    pressed: '&[data-pressed="true"]',
```

> Далее мы можем применить условие в стилях рецепта.

```
_pressed: {
  bgColor: 'button.primary.default.bgPressed',
},
```

#### **Пример с вариантом в рецепте**.

При условии когда мы должны использовать пропсы, такие как, `isSelected`, `isPressed`, `isHover`, `isPending` и.т.д.
Вместо передачи пропсов через аттрибуты мы можем передать их напрямую в рецепт.

```
//Передача пропсов в рецепт
export const SomeComponent: FC<SomeComponentProps> = (props) => {
  const { isPending, isDisabled, ...otherProps } = props;
  const classNames = someComponentRecipe({isPending, isDisabled})
```

```
// Использование пропcов в рецепте
  variants: {
    isDisabled: {
      true: {
        root: {
          backgroundColor: 'background.tertiary',
        },
      },
    },
    isPending: {
      true: { root: { pointerEvents: 'none' } },
    },
  },

// Комбинирование значений для получения зависимых состояний друг-от-друга
  compoundVariants: [
    {
      isDisabled: true,
      isPending: false,
      css: {
        root: {
          cursor: 'not-allowed',
          backgroundColor: 'background.tertiary',
        },
      },
    },
  ],
```

- **Адаптивность:** - Адаптивная верстка следует по принципу [Mobile First](/docs/foundation-resposive--docs). Это подход к разработке веб-дизайна
  и пользовательских интерфейсов, где проектирование начинается с
  наименьших экранов, таких как смартфоны, а затем масштабируется
  для больших экранов (`планшеты`, `десктопы`).
  Узнайте больше о возможностях [адаптивной верстки с PandaCss](https://panda-css.com/docs/concepts/responsive-design)

```
{
  // mobile
  background: 'red.300',

  w640:{
  // tablet, desktop
    background: 'green.300',
  }
}
```

- **Правила хорошего тона:** - Существуют общие правила написания кода, так как PandaCSS имеет корни и принципы разработки от Chakra.io.
  То при написании стилей в PandaCSS могут использоваться сокращения например `px, py, bg, mt, h` и.т.д.
  В команде мы договорились что подобные сокращения мы **НЕ используем** и по возможности пишем целиком, для повышения читаемости кода.

```
px - paddingInline
py - paddingBlock
bg - background
mt - marginTop
h - height
и.т.д.
```

### Наименования Токенов и Компонентов

В большинстве случаев все наименования компонентов и токенов диктуются дизайн макетами в Figma.
Наименования должны дублировать названия компонентов и токенов из макетов.
Случается, что дизайнеры допускают ошибки и токены которые предназначены для других компонентов используются
не по назначению. Например, в компоненте `Tabs` дизайнер применяет токены которые относятся к кнопкам `button.default.fgHover`,
в таком случае надо проговорить с дизайнером данный кейс,
чтобы внесли соответствующие правки и уже тогда добавить недостающие токены.

> Избегайте в наименованиях словосочетаний которые несут логическую привязку к цвету, допустим
> `buttonWhiteBorder`,`buttonFilledGray`. У нас заложена поддержка мультитемы,
> и привязка к цвету актуальна только в основной теме,
> в остальных вариантах будет использоваться другой цвет и подобная привязка теряет всякий смысл.

### Пропсы

Внедренные библиотеки предоставляют инструменты для решения ряда задач которые встречаются при разработке или поддержке компонентов.

- **splitVariantProps**
  Разделение входящих пропсов на два типа:
  пропсы которые нужны для стилей и они описаны в рецепте как варианты и все остальные пропсы.
  [Ознакомиться с концептом SplitRecipe](https://panda-css.com/docs/overview/faq#how-do-i-split-recipe-props-from-the-rest)
  Данный подход широко используется при разработке компонентов, избавляет от возможности передачи ненужных пропсов которые могут сломать логику компонента, а также уменьшает кол-во написанного кода.
  `const [styleProps, restOfProps] = someRecipe.splitVariantProps(props)`

- **cx** - вспомогательная функция позволяет совмещать стили рецепта и стили написанные отдельно.
  Функция возвращает готовые классы которые мы можем передать напрямую в `className` тэга HTML.

[Ознакомиться с концептом CX](https://panda-css.com/docs/concepts/merging-styles#merging-config-recipe-and-style-object)

```
import { css, cx } from '#styled-system/css';

export function Button(props: ButtonProps) {
  const { children, ...rest } = props
  const [buttonProps, cssProps] = button.splitVariantProps(rest)
  return (
    <button className={cx(button(buttonProps), css(cssProps))}>
      {children}
    </button>
  )
}
```

- **mergeProps** - Объединяет несколько объектов props вместе.
  Обработчики событий объединяются в цепочки, classNames комбинируются,
  а идентификаторы `id` удаляются дублирующиеся — разные `id` вызовут побочный эффект и повторный рендер компонентов,
  подключённых с помощью `useId`. Для всех остальных props, последний объект props переопределяет все предыдущие.

[Ознакомиться с mergeProps](https://react-spectrum.adobe.com/react-aria/mergeProps.html#mergeprops)

```

// Пример на реальном компоненте из дизайн системы IconButton

import { mergeProps } from 'react-aria';

export function IconButton(props: ButtonProps): ReactElement {
  const [variantProps, otherProps] = buttonRecipe.splitVariantProps(props);
  const buttonVariantContext = useContext(ButtonVariantContext);

  const mergedVariantProps = mergeProps(buttonVariantContext, variantProps);

  const buttonClassName = buttonRecipe({
    ...mergedVariantProps,
    onlyIcon: true,
  });

  return <AriaButton {...otherProps} className={buttonClassName} />;
}
```

### Позиционирование компонента и почему компоненты дизайн-системы не должны иметь внешние отступы (padding или margin)?

Компоненты дизайн-системы **не должны содержать внешние отступы** по нескольким важным причинам:

#### 1. **Гибкость и переиспользуемость**

Компоненты должны быть максимально универсальными и легко встраиваться в разные контексты. Если компоненты имеют жёстко заданные внешние отступы, это ограничивает возможность гибкого их использования в различных макетах.

_Пример:_ В одном месте может понадобиться большее расстояние между элементами, в другом — меньшее. Внешние отступы должны задаваться на уровне макета, а не компонента.

#### 2. **Контроль над композицией**

Управление отступами на уровне контейнеров (родительских элементов) даёт дизайнерам и разработчикам больше контроля над композицией и внешним видом макета.

_Пример:_ Родительский компонент или контейнер может самостоятельно управлять расстоянием между дочерними элементами, поддерживая общую структуру дизайна.

#### 3. **Совместимость и масштабируемость**

Отсутствие жестких внешних отступов делает компоненты совместимыми с различными темами и сетками. Это важно при адаптивной разработке, где плотность и расстояния могут изменяться в зависимости от устройства или контекста использования.

_Пример:_ На мобильных устройствах могут использоваться более узкие отступы, а на больших экранах — более широкие.

#### 4. **Следование принципу "responsibility of layout"**

Этот принцип гласит, что за позиционирование и расстояние между элементами отвечает родительский элемент или контейнер, а не сам компонент. Компонент должен отвечать только за свое внутреннее содержимое.

---

Таким образом, компоненты без внешних отступов проще управляемы, лучше адаптируются под разные макеты и темы, и обеспечивают большую гибкость при разработке интерфейсов.

### Storybook

При написании `stories` (демо представление компонента) нам необходимо соблюдать несколько факторов.

- Подготовить короткое описание к компоненту. Что за компонент, какую функцию он выполняет, его **особенности**, где **применяется** если есть специфичные детали также добавляем как **примечание**.

- В большинстве случаев **пропсы** которые относятся к стилям или статусам уже сгенерированны сборщиком PandaCSS или есть в типизации **RAC**. Надо по максимуму использовать готовые типы и по возможности избегать написания ручных типов.

- Проверяем наличие необходимых контролов для стори если что добавляем (дать ссылку на Storybook controls )
  [Полезные методы PandaCSS которые используются для мапинга возможных вариантов компонента](https://panda-css.com/docs/concepts/recipes#methods-and-properties)

```

buttonRecipe.variantKeys
// => ['size']

buttonRecipe.variantMap
// => { size: ['sm', 'md'] }
```

Описание контролов в сторе компонента.

```
  argTypes: {
    variant: {
      control: { type: 'radio' },
      options: buttonRecipe.variantMap.variant,
    },
    colorScheme: {
      control: { type: 'select' },
      options: buttonRecipe.variantMap.colorScheme,
    },
```
